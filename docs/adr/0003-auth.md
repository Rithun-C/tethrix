# ADR-0003: Authentication (sign-in, tokens, local development)

- Status: Accepted 2026-11-15
- Date: 2026-11-15
- Task: I-06
- Stories: US-01 to US-04, US-61

## Context

Users sign in with email, password and an authenticator app (MFA). Only the admin creates
accounts. The API must know who is calling on every request, and the user ID must come
from a token the server can verify, never from the browser.

Constraints from ADR-0002: the browser's `Authorization` header is replaced by
CloudFront's signature, so the token needs another header.

Words used below:

- Cognito user pool: AWS's user directory. It stores users and passwords and issues tokens.
- JWT (JSON Web Token): a signed piece of JSON saying who you are and until when. Anyone
  can read it; only Cognito can sign it, so the server can check it was not forged.
- Access token: the JWT the API checks. Lives 1 hour.
- Refresh token: used by the app to get a new access token without signing in again.
- OAuth 2.0 / OpenID Connect (OIDC): the standard sign-in protocols Cognito speaks.
- PKCE: an extra check in the OAuth flow that stops a stolen sign-in code from being used
  by anyone else.

## Decisions

### 1. User pool

| Setting | Value | Why |
|---|---|---|
| Feature plan | Lite | Cheapest. 10,000 monthly users free. No paid Plus features |
| Self sign-up | Off (`AllowAdminCreateUserOnly`) | I-01: admin creates accounts |
| Sign-in name | Email | |
| MFA | Required, authenticator app (TOTP) only | US-02. No SMS: it costs money and is weaker |
| Password policy | At least 14 characters, mixed types | Same as the IAM policy (G-08) |
| Account recovery | Email | |
| Deletion protection | On | |

### 2. Sign-in flow: Cognito hosted sign-in page, authorization code flow with PKCE

The React app sends the user to Cognito's own sign-in page. Cognito handles the password
and the MFA code, then redirects back to the app with a one-time code. The app swaps that
code for tokens.

Why this and not our own sign-in form:

- The password never touches our code.
- MFA setup and challenges are handled by Cognito.
- It is the standard OAuth flow used by most real apps, so it is worth learning.

The frontend uses a standard OIDC client library (candidate: `oidc-client-ts`). The exact
package is checked and pinned in B4.

### 3. Token header: `X-Auth-Token`

The browser sends the access token as `X-Auth-Token: <jwt>`. CloudFront forwards this
header to Lambda (ADR-0002). Lambda never sees a user token in `Authorization`.

### 4. Token checks in FastAPI (every request except `/health`)

A FastAPI dependency checks the token:

1. Signature is valid, using Cognito's public keys (JWKS), cached in memory.
2. Algorithm is RS256. `none` and any other algorithm are rejected.
3. `iss` is our user pool, `exp` is in the future, `token_use` is `access`,
   `client_id` is our app client.
4. The user's profile item exists in DynamoDB. If it does not (the account was deleted),
   the request gets 401.

Step 4 is what makes US-61 work: after account deletion, an old access token is still
correctly signed until it expires, so the signature check alone would accept it. The
profile check costs one small database read, and the profile is needed for the time zone
anyway.

The user ID is the token's `sub`. It is passed to the data layer, which builds every key
from it (`USER#<sub>`, see I-08).

Library: `PyJWT` with its `cryptography` extra. The exact package and version are checked
and pinned in B4.

### 5. Sessions and sign-out (US-03)

| Setting | Value |
|---|---|
| Access token lifetime | 60 minutes |
| Refresh token lifetime | 12 hours (a hard cap on any session) |
| Inactivity sign-out | The app signs out after 60 minutes without user activity |
| Sign-out | Revokes the refresh token at Cognito and clears tokens in the browser |

### 6. Token storage in the browser

- Access token: in memory only.
- Refresh token: in `sessionStorage`, cleared when the tab is closed.

Trade-off: tokens in the browser can be stolen by an XSS bug. That risk is reduced by
the XSS defences (US-42, Content Security Policy in B3), the short lifetimes above, and
it is recorded in the threat model. The alternative (a backend that holds tokens in
cookies) is more secure but much more work; it is noted as theory.

### 7. Local development (Docker Compose)

Cognito cannot run on a laptop. Instead of skipping authentication locally, the backend
uses the same token checks with a different trusted issuer:

- A small local script creates test tokens signed with a local development key.
- In local mode, the backend trusts that key instead of Cognito's.
- Everything else (signature, expiry, profile check, `sub` as user ID) is identical.

Guards, so local mode can never run in AWS:

- The backend refuses to start in local mode if it detects it is running in Lambda
  (the `AWS_LAMBDA_FUNCTION_NAME` environment variable is set).
- Terraform never sets the local-mode setting.
- A test checks both rules.

### 8. Admin creates users (US-01)

A runbook command: `aws cognito-idp admin-create-user`. Cognito emails a temporary
password, and the user must set a new password and MFA at first sign-in. Cognito's
built-in email sender (a small free daily limit) is enough for a few test users.

## Options considered and not chosen

| Option | Why not |
|---|---|
| Our own sign-in form with Cognito's API | More code, and our app would handle passwords and MFA challenges |
| Token check in API Gateway instead of FastAPI | Requires API Gateway (rejected in ADR-0002) |
| Tokens in cookies held by a backend (BFF pattern) | Safer against XSS but much more work; documented as theory |
| Turning auth off locally | Risks a bypass reaching AWS; the threat model flags this (T-004) |

## Consequences

- Every request makes one small DynamoDB read for the profile.
- A signed-out user's access token keeps working for up to 60 minutes unless the account
  is deleted. Accepted, and recorded in the threat model.
- The hosted sign-in page looks like Cognito, not like our app. Accepted.
- Callback and sign-out URLs must be the CloudFront domain, known after B3.
